# Data

Nothing in this repository is a real call, a real dispatch record or a real
person. This page lists every source of data and says which numbers are
synthetic, which are fitted, and which come from a published report.

## Summary

| Data | Where | Real or synthetic |
|-|-|-|
| Scripted calls (3) | `backend/app/services/call_session.py` | Fictional, hand-written |
| Evaluation cases | `backend/eval/data/*.yaml`, `backend/eval/missed_escalations.py`, `backend/eval/bias_pairs.py` | Fictional, hand-written, marked `synthetic: true` |
| Evaluation results (v1) | `backend/eval/results/v1/` | Real model output on fictional input |
| Demo extraction fixture | `backend/eval/fixtures/demo_scripts.json` | Hand-written ideal extraction (`"recorded": false`) until recorded |
| Synthetic audit month | generated by `backend/app/services/synthetic.py` | Synthetic, seeded |
| Arrival model | `backend/app/data/arrival_model.yaml` | Fitted and illustrative; see below |
| Rulebook | `backend/rules/dispatch.yaml` | Illustrative assumptions |
| Call log | `backend/data/despatch.db` (created at run time, not committed) | Whatever you do in the console |

## The arrival model

`backend/app/data/arrival_model.yaml` drives both the synthetic audit month and
the What-If simulator. Each set of numbers has a `source` next to it.

| Numbers | Provenance |
|-|-|
| Hour-of-day weights (24) | **Fitted.** Chosen so schedule coverage reproduces the four figures below. Not a LEAP table. |
| Day-of-week weights (7) | **Fitted**, same way. |
| Call-type mix | **Illustrative.** Not LEAP data. |
| 47 calls per week | From the project plan: about 2,420 community-responder-appropriate calls per year in LEAP's analysis of 2019 calls. **Not re-checked against the report.** |
| 62% on the non-emergency line | From the project plan. **Not re-checked against the report.** Used only to label synthetic audit records. |

### What "fitted" means, and why it matters

The project plan contained a table of schedule coverage, calculated from
LEAP's 2019 hour-of-day and day-of-week breakdowns on the assumption that hour
and day are independent:

| Schedule | Share of calls covered |
|-|-|
| Weekdays, 8 AM to 4 PM | 22% |
| Weekdays, 8 AM to 8 PM | 36% |
| Every day, 8 AM to 8 PM | 55% |
| Every day, 9 AM to 2 AM | 87% |

The weights in the data file were chosen to reproduce those four numbers. So:

- `coverage()` returning 22 / 36 / 55 / 87% is the fit working, not a
  validation against call data.
- The simulator handling about 87% of calls with unlimited teams on the
  9 AM to 2 AM schedule shows that the simulator agrees with its own inputs.
- The shape between the fitted points (for example, exactly which evening hour
  is busiest) is an assumption.

That is why the file says `provenance: fitted` and every API response that
uses it says `calibrated_to_leap: false`.

### Calibrating for real

LEAP's report is public: Law Enforcement Action Partnership, *Amherst
Community Responder Report* (November 2021),
https://pelhamma.gov/files/Leap_Amherst_Community_Responder_Report_Final.pdf.
The PDF is not stored in this repository.

To replace the fit with the report's own figures:

1. Transcribe the report's hour-of-day and day-of-week distributions into
   `hour_weights.values` and `day_weights.values` as shares that sum to 1.
   Put the page number in each `source`.
2. Do the same for the call-type mix, the weekly volume and the
   non-emergency-line share if the report gives them, with page numbers.
3. Set `provenance: leap_tables`.

Nothing else changes: the file is validated at load, and the API then reports
`calibrated_to_leap: true` for arrival timing. The four coverage figures above
become a genuine cross-check (they should land near, not exactly on, the
table), and `tests/test_leap_arrivals.py` will need its tolerances reviewed.
If the report gives only marginal distributions, keep the sentence about
independence.

## The synthetic audit month

`generate_synthetic_month()` draws each call's time and type from the arrival
model, then invents the rest. Every rate below is a named constant in
`synthetic.py` and none is measured:

| Assumption | Value |
|-|-|
| When CRESS "actually" works | Weekdays 8:00 to 16:00 |
| Share of referable, on-duty, no-concern calls that dispatch "actually" refers | 25% |
| Share of other on-duty calls sent to CRESS anyway (a misroute) | 3% |
| Calls with one screening answer "yes" | 8% |
| Calls with one screening answer unknown | 5% |
| "Actual" destination otherwise | fire/EMS if injured, else police |

The "actual dispatch" column is deliberately generated independently of the
rulebook so that the audit has something to disagree with. It says nothing
about what any real dispatch centre does. The default month is 250 calls,
seed 42, November 2026; the same seed gives the same month.

## The simulator's other assumptions

Listed in the API response and on screen (`ASSUMPTIONS` in `simulator.py`):
every eligible on-duty call goes to CRESS; no queue and no travel time; a call
that arrives when every team is busy is missed; call length is the configured
average times a log-normal multiplier with mean about 1, clipped to 0.25 to 4;
utilization counts only minutes inside the shift; CRESS's direct work is not
modelled. Each comparison runs both schedules on the same generated calls, 50
replications by default, seeds 42 to 91.
